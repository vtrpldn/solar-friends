# Cooperative saved-draft opening and history limits

Why: saved histories were validated synchronously twice while opening a creation. Large journals need progress and cancellation before replacing the current editor, with the same exact replay, byte limits and corruption policy.

Document restoration now shares one generator between synchronous and cooperative APIs. Cooperative restoration takes an owned snapshot, checks its serialized shape/size boundary before a large ownership copy, yields between normalization/replay steps and honors abort without returning a partial document. Original definition limits, exact history signatures, 64-step/8-MiB entry budgets, legacy migration and corrupt-history recovery remain. Unknown outer checkpoint/history metadata is not copied.

Heavy maps or large journals open through separate native compilation and cooperative history restoration, with one progress dialog kept open through asynchronous finalization. The already checked document and native checkpoint are reused at attachment. No invalid preview is installed. Cancellation preserves both current and target creations; a fresh storage revision check rejects a target changed by another author during opening. Edit regains focus after canceled/failed library opening, and direct-URL Escape leaves a usable focused library.

Both native-valid fixtures contain 256 mixed buildings, 1000 macambira objects and 64 installed electrical routes, authored five, resolved 4096-cell soil and no river. The step fixture seeds 80 valid title edits and retains 64 (15,314 history bytes); public controls replay all 64 Undo and all 64 Redo with whole-definition comparison against independently reconstructed states, branch away from Redo, save and reload exactly. The byte fixture seeds 20 whole-property fertility changes and retains 17 (8,269,405 history bytes); another author adds a title change, then public controls replay all 18 Undo/Redo states, keep byte limits and reload exactly. Setup uses document/library APIs, not 80 public authoring gestures.

Opening Cancel and cancellation while client-side history restoration is deliberately held both preserve source and current checkpoints and URL. Releasing the canceled finalizer cannot install it. A real second-page library writer changes the target while native preparation is held; stale installation is refused and the fresh checkpoint remains intact. Measured phases have no synchronous public restore or main-thread scenario compilation. All 173 observed preparation workers terminate; no page errors, bounded cleanup completes before the main report records success.

Final sampled cooperative restore slices peak at 13.1–16.0 ms for the 64-step fixture and 108.8–116.0 ms for the byte-heavy fixture; byte-history snapshot/copy work remains a performance concern. These are short instrumented headless observations, not 60-fps or sustained hardware/memory acceptance. Separate near-limit save regression (8,078,050 bytes/16 steps) passes exact reload, coalescing, queued newer edits, preparation failure/retry and previous/current preservation; its sampled Save timer gap is 38 ms.

Direct document checks pass exact 64-step replay, legacy/corruption parity, ownership under caller mutation, early/mid cancellation, failed yields, oversized journals, ignored extra metadata and nonfinite definitions. Existing 700-sequence journal checks pass. Controlled asynchronous-finalizer browser checks pass success once, Cancel/Escape, timeout/rejection, signal abort, worker termination and late-result isolation. Native preparation parity/playtest and final-source stored-checkpoint fallback regressions pass; damaged originals are preserved and incomplete drafts remain editable.

Both final full desktop captures individually inspected: readable opening progress/Cancel over the library and the restored byte-limit draft. This is not artwork acceptance.
